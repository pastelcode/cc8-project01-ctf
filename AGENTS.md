# AGENTS.md

## Core Cognition & Meta-Prompting

1. **Intent Extraction:** Analyze user prompts to isolate the true technical problem before writing any code. This is a multiplayer game — always consider both server-side and client-side implications of every change.
2. **Deterministic Architecture:** Adhere strictly to the patterns defined in `MEMORY.md`. The layered architecture (`core/` → `network/` → `server/` | `client/`) is non-negotiable. Never introduce ad-hoc architectural drift.
3. **Plan-First Protocol:** Propose a modular, step-by-step modification blueprint. Wait for explicit user validation before modifying files.
4. **Continuous Verification Loop:** After every code change, run `dart format`, `flutter analyze`, and relevant tests. If verification fails, self-heal the regression before reporting completion.
5. **Memory:** Before performing any implementation work:
   1. Read `MEMORY.md` to understand persistent project knowledge.
   2. Read `CURRENT_SPRINT.md` to determine the active objective.
   3. Load only the documentation required for the current task.
   4. After implementation, synchronize:
      - `CURRENT_SPRINT.md` if execution state changed.
      - `IMPLEMENTATION_PLAN.md` if roadmap progress changed.
      - `CHANGELOG.md` if work was completed.
      - `MEMORY.md` only if long-term project knowledge changed.

## Absolute System Guardrails (Anti-Patterns)

- NEVER drop, prune, or truncate code files to "save space" or "simplify."
- NEVER change the protocol message format without updating SPEC-backed Freezed models.
- NEVER import a third-party networking library — `dart:io` raw sockets only (per SPEC §1.1).
- NEVER bypass or use `--no-verify` on failing linters or test executions.
- NEVER invent new protocol messages or error codes — the catalog is closed per SPEC §2.3.
- NEVER introduce new dependencies without checking `pubspec.yaml` first and justifying the addition.
- NEVER allow a UI widget to import from `server/`, or server logic to import from `client/`. These layers are isolated.

## Project-Specific Conventions

### Code Generation

Always run code generation after modifying annotated files:

```bash
dart run build_runner build --delete-conflicting-outputs
```

Files that require regeneration:

- Any file with `@freezed` annotation → `*.freezed.dart` + `*.g.dart`
- Any file with `@riverpod` annotation → `*.g.dart` (via `riverpod_generator`)

### Protocol Compliance

Every message type must match the SPEC v1.2.0 catalog exactly. Cross-reference with `docs/SPEC.md` when implementing:

- Field names: use `@JsonKey(name: 'snake_case')` for wire format
- `flag.owner`: `null` (never `0` or `""`)
- `type` field: auto-generated by Freezed discriminator
- Message size: enforced at ≤ 64 KB per SPEC §2.1

### Logging

Use `logger` package. In debug mode, log every sent and received protocol message via `logMessage(direction, rawJson)` from `lib/shared/logger.dart`.

### Enums Over Strings

All protocol values with a known set of options MUST be enums with `@JsonValue` annotations. See `lib/core/messages.dart` for the canonical definitions:

- `ServerState` — `lobby`, `playing`
- `GamePhase` — `lobby`, `countdown`, `playing`, `gameOver`
- `ErrorReason` — all 11 SPEC error codes

## Documentation Ownership Matrix

| Information                                                         | Owner                    |
| :------------------------------------------------------------------ | :----------------------- |
| Stable project knowledge (vision, architecture, stack, conventions) | `MEMORY.md`              |
| Current execution (sprint objective, active tasks, blockers)        | `CURRENT_SPRINT.md`      |
| Future implementation (milestones, backlog, roadmap)                | `IMPLEMENTATION_PLAN.md` |
| Completed work (added, changed, fixed, removed)                     | `CHANGELOG.md`           |

If information appears in multiple documents, it has been placed incorrectly. Documentation ownership must remain unique.

## Documentation Synchronization Rules

Whenever code changes, determine whether documentation must also change:

| Scenario              | MEMORY | CURRENT_SPRINT | IMPLEMENTATION_PLAN | CHANGELOG |
| :-------------------- | :----: | :------------: | :-----------------: | :-------: |
| New feature completed |        |       ✓        |          ✓          |     ✓     |
| Architecture decision |   ✓    |    Optional    |                     |     ✓     |
| Sprint progress       |        |       ✓        |          ✓          |           |
| Technology migration  |   ✓    |    Optional    |                     |     ✓     |
| Roadmap reprioritized |        |                |          ✓          |           |
| Bug fix merged        |        |    Optional    |                     |     ✓     |

Never update documents "just in case." Update only the document that owns the affected information.

## AI Operating Principles

- Every document has one responsibility.
- Every piece of information has one owner.
- Documentation drift is a bug.
- Documentation updates are part of the implementation.
- Load the minimum context required to complete the task.
- Never load documentation that is unrelated to the active task.
- When in doubt about protocol behavior, consult `docs/SPEC_EN.md` — the spec is authoritative.
